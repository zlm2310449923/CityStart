CityStart 小组项目最终任务分配
1. 项目基本信息
项目名称：
CityStart：新市民安居与就业一站式服务平台
英文名称：
CityStart: A One-Stop Settlement and Employment Service Platform for New Urban Residents
项目背景：
以武汉市真实公共服务流程和官方办事资料为参考，设计一个统一平台，帮助新市民完成居住、就业和住房相关事项。系统为课程原型，不连接真实政府数据库，不使用真实个人敏感信息。
服务提供者与服务范围
服务提供者	服务
公安政务部门	S1 居住登记；S2 居住证申请
人力资源和社会保障部门	S3 就业登记；S4 就业扶持资格申请
住房保障部门	S5 公租房资格申请；S6 住房租赁补贴申请
三个重点业务流程
	•	P1：居住证申请与补充材料流程
	•	P2：住房租赁补贴申请与资格核验流程
	•	P3：就业登记与就业扶持申请流程
系统模块
citystart-portal
api-gateway
residence-service
employment-service
housing-service
service-matching-service
项目最终需要覆盖服务识别与BSRL、三层ArchiMate、至少3个真实BPMN流程及语义效果、SoaML、至少3个微服务，以及至少2个流程的事件日志与流程挖掘。每周还需要真实会议记录和成员实际成果证据。

大家好，因为现阶段各模块由负责人独立开发、后期再统一集成，为避免最后出现语言、端口、字段和数据库无法对应的问题，现确定以下 CityStart Technical Baseline。该基线只统一影响集成的部分，各模块内部实现方式仍由负责人自行决定。

一、统一技术选型

1. 后端统一使用 Python 3.12。
2. Residence、Employment、Housing、Matching Service和API Gateway统一使用FastAPI、Pydantic v2和Uvicorn。
3. API Gateway调用其他服务时使用HTTPX。
4. Portal原则上使用HTML、Bootstrap和JavaScript fetch，不增加React、Vue等额外框架，除非F和E确认确有需要。
5. 服务之间统一使用HTTP REST和JSON通信。

二、服务及端口

* CityStart Portal：3000
* API Gateway：8000
* Residence Service：8001
* Employment Service：8002
* Housing Service：8003
* Service Matching Service：8004

端口和服务地址必须通过配置或环境变量管理，不要在业务代码中到处写死。

三、数据库与文件处理

1. Residence Service、Employment Service和Housing Service分别管理自己的SQLite数据库，不使用共享数据库：

   * residence.db
   * employment.db
   * housing.db
2. Matching Service保持stateless，不设置数据库。
3. Portal和Gateway不直接访问业务数据库。
4. 当前项目使用模拟数据，不连接真实政府数据库。
5. 申请材料原则上只保存document_id、application_id、document_type、file_name、verification_status和uploaded_at等模拟记录，不增加云存储或复杂文件系统。确需演示文件上传时，再由对应服务使用本地uploads目录处理。

四、统一接口格式

1. 字段名称统一使用snake_case。
2. 时间统一使用ISO 8601格式，例如：
   2026-08-05T10:30:00Z
3. HTTP请求和响应统一使用JSON。
4. 服务名称和编号必须统一使用S1—S6，不自行修改正式英文名称。
5. 状态值统一使用小写英文，例如：
   pending、under_review、approved、rejected、additional_documents_required。
6. 错误响应统一采用以下结构：

{
"error": {
"code": "VALIDATION_ERROR",
"message": "The request body is invalid.",
"details": []
}
}

五、调用关系

系统调用关系固定为：

Citizen → Portal → API Gateway → Microservices

Portal只能调用API Gateway，不能直接调用Residence、Employment、Housing或Matching Service，也不能直接访问数据库。

Gateway负责路由转发、服务组合、超时处理、服务不可用处理和统一错误返回。

六、各模块最低交付内容

每个后端模块需要提供：

* 完整源代码；
* requirements.txt；
* README和启动方法；
* .env.example或配置说明；
* 数据库初始化方法或示例数据；
* Swagger测试结果；
* 至少4个测试案例；
* 示例Request和Response。

Matching Service至少提供5个测试案例，目前A的独立版本已经完成10个规则测试。

七、API冻结流程

1. B、C、D分别整理自己服务的Endpoint、Request Fields、Response Fields、Status Values和示例数据，提交给E。
2. A向E提供Matching Service的API Contract。
3. E负责汇总Endpoint List、字段、状态、错误格式、端口和环境变量，形成统一API Baseline。
4. A检查服务名称以及BSRL、BPMN、ArchiMate、SoaML、API和Event Log之间是否一致。
5. API确认后不得私自修改。确需修改时，需要说明原因和受影响模块，由E确认技术影响、A确认跨模型影响，并同步更新接口文档。

八、成员可以自行决定的内容

在不改变统一接口的情况下，各负责人可以自行决定：

* 服务内部文件夹结构；
* 函数和类的组织方式；
* 使用sqlite3或SQLAlchemy；
* 数据库内部表结构；
* 单元测试组织方式；
* Portal具体页面样式；
* 模块内部规则实现。

请大家检查自己的模块是否与以上基线存在冲突。如有问题及时提出，确认后再按照统一基线继续开发，避免最后集成阶段集中修改。
