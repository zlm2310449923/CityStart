## F.1 Front-end Design

### F.1.1 Design constraints

The Portal's design is determined more by the CityStart Technical Baseline than
by aesthetic preference. Four clauses shape it directly:

- **§1.4** restricts the front end to HTML, Bootstrap and JavaScript `fetch`.
  React and Vue are excluded. The Portal therefore uses server-rendered Jinja2
  templates with progressive client-side enhancement, not a single-page
  application.
- **§5** fixes the call chain as `Citizen → Portal → API Gateway → Microservices`.
  The Portal may not call a business service or a database directly.
- **§2** requires addresses to come from configuration. No host or port appears
  in page logic.
- **§4.6** mandates a single error envelope, which determines how the client
  reports every failure.

### F.1.2 Consequences of the §5 constraint

Enforcing §5 is the most consequential design decision in this module. Two
options were available:

1. Let the browser call the Gateway directly at `localhost:8000`.
2. Route browser calls through the Portal server, which forwards to the Gateway.

Option 2 was chosen. Under option 1 the Gateway would need CORS configuration
for the Portal's origin, and the Gateway's address would be exposed in
client-side JavaScript, where any page could be edited at runtime to call a
service directly — §5 would hold only by convention. Under option 2 the browser
has exactly one origin, the Gateway needs no CORS handling, and §5 is
structurally enforced: the browser has no route to any service.

An earlier iteration of this module included an `/api/direct/*` route that
mapped service names to individual ports for debugging. That route violated §5,
because it gave the Portal a path that bypassed the Gateway entirely. It has
been removed rather than merely left undocumented, so that compliance can be
confirmed by reading `app.py` instead of trusting that nobody calls it.

### F.1.3 Technology choices

| Concern | Choice | Reason |
|---|---|---|
| Server framework | Flask 3 | Minimal; same Python 3.12 runtime as the FastAPI services (§1.1) |
| Templating | Jinja2 | Listed as permitted; gives shared layout without a build step |
| CSS | Bootstrap 5.3 via CDN | Permitted by §1.4; responsive grid with no bundler |
| Client logic | Vanilla JS, `async/await` | §1.4 forbids frameworks |
| HTTP client | httpx | §1.3 specifies httpx for service-to-service calls |

Flask was chosen over FastAPI for the Portal specifically because the Portal
serves HTML rather than JSON. FastAPI's advantages — Pydantic validation and
automatic OpenAPI generation — apply to API surfaces, and the Portal exposes no
API of its own beyond the proxy.

## F.2 Portal Implementation

### F.2.1 The proxy

`app.py` exposes one outbound route, `/api/proxy/<path>`, supporting GET, POST,
PATCH, PUT and DELETE. It forwards query parameters and JSON bodies unchanged.

Error handling distinguishes two categories, which matters for diagnosis:

- **Upstream errors are passed through untouched.** A 404 or a 422 from a
  service reaches the browser with its original status and body. Wrapping these
  would destroy the field-level validation details the user needs.
- **Portal-originated failures are generated locally**, using the §4.6 envelope:

| Code | HTTP | Condition |
|---|---|---|
| `GATEWAY_UNAVAILABLE` | 503 | Connection to the Gateway failed |
| `GATEWAY_TIMEOUT` | 504 | No response within `GATEWAY_TIMEOUT_SECONDS` |
| `GATEWAY_INVALID_RESPONSE` | 502 | Response body was not valid JSON |

### F.2.2 A diagnostic defect found during testing

Testing UAT-05 (Gateway unavailable) initially produced `GATEWAY_INVALID_RESPONSE`
rather than the expected `GATEWAY_UNAVAILABLE`, even with no process listening on
port 8000. The cause was a system-wide HTTP proxy configured on the development
machine. httpx honours proxy environment settings by default, so the request was
routed to the local proxy, which returned its own non-JSON 502 error page. The
Portal correctly observed "a reply that is not JSON" and reported it as such.

The behaviour was not wrong, but the diagnosis it produced was misleading: an
operator seeing `GATEWAY_INVALID_RESPONSE` would investigate the Gateway's
serialisation logic rather than notice that the Gateway was not running at all.
Since the Gateway is always a local or internal address, the proxy is now
bypassed for these calls (`trust_env=False`), with `PORTAL_TRUST_ENV_PROXY=1`
available if a deployment genuinely places the Gateway behind a proxy. The test
now yields `GATEWAY_UNAVAILABLE` (503).

This is recorded because it illustrates a general risk in distributed
integration: an error path can be technically correct and still point the reader
at the wrong component.

### F.2.3 Client-side helpers

`static/js/main.js` centralises three concerns:

**Unified error extraction.** `extractError()` reads the §4.6 envelope, and also
accepts FastAPI's native `{"detail": ...}`, including Pydantic's list form,
which it flattens into `field: message` text. Services not yet migrated to §4.6
therefore still produce readable messages instead of `undefined`.

**Status vocabulary.** `STATUS_LABELS` maps exactly the five §4.5 values to
Bootstrap badge classes. An unrecognised value degrades to a neutral badge
rather than throwing, so a non-compliant service response is visibly wrong
without breaking the page.

**HTML escaping.** All server-supplied values pass through `escapeHtml()` before
insertion. Even with simulated data, building innerHTML from response fields
without escaping is an injection path.

### F.2.4 Page behaviour

Each service page carries a submission form and, where the API supports it, a
query panel. Forms rely on HTML5 `required` for immediate feedback and on
server-side validation for authority. On success the returned `application_id`
is copied into the query field, so the demonstration does not require reading an
ID off the screen and retyping it.

### F.2.5 Process Analytics page

This page contains no hard-coded figures. On load it fetches
`static/analytics.json` and renders the comparison table, per-process variant,
bottleneck, outcome, resource and conformance sections, and the discovered-model
summary. If the file is absent it displays the commands needed to generate it.

This design followed from a defect in an earlier draft, where the page and the
report each contained separately typed figures that had drifted apart. Deriving
both from one generated artefact removes the possibility.

## F.3 Event Log Generation

### F.3.1 Division of responsibility

The group split assigns the P1 log to B and the P2 log to D, and assigns F the
task of *integrating* them. Integration here is a validation gate, not
concatenation: the two logs are produced by different developers from different
services, and any disagreement between them and the BPMN models invalidates
every conclusion drawn later in this chapter.

F additionally maintains a seeded reference generator
(`generate_logs.py`). Its purpose is to make F's analysis pipeline and the
demonstration developable before B and D deliver, and to guarantee that a
known-good log set always exists. When real logs arrive they are placed in
`logs/incoming/` and processed by the identical pipeline.

### F.3.2 Log schema

The group specification names the fields `process_name` and `service_name`; the
supplementary specification names them `process_id` and `service_id`. Rather
than choose one and create a mismatch with whichever member followed the other
document, both are emitted, and the validator derives either from the other if
only one is supplied.

| Field | Meaning |
|---|---|
| `case_id` | Case identifier, e.g. `P1-C0001` |
| `process_name` / `process_id` | Process identity |
| `service_name` / `service_id` | Business service (S1–S6) |
| `activity` | Must equal a BPMN Task name exactly |
| `timestamp` | ISO 8601 UTC with `Z` suffix (§4.2) |
| `resource` | Executing organisational unit |
| `lifecycle` | XES lifecycle transition |
| `outcome` | Activity-level outcome |
| `application_status` | Case status, from the §4.5 vocabulary |
| `duration_hours` | Elapsed time attributable to the activity |
| `variant` | Designed variant label, for validation only |

Two Baseline clauses apply directly. Under **§4.2** timestamps are UTC with a
`Z` suffix, so the log, the REST APIs and the report express time identically.
Under **§4.5** `application_status` uses only `pending`, `under_review`,
`approved`, `rejected` and `additional_documents_required`. An earlier draft used
`submitted` and `pending_documents`, which appear nowhere in the Baseline; had
they survived, the mining chapter would have described a different state machine
from the API chapter.

### F.3.3 Duration semantics

`duration_hours` is the elapsed time attributable to completing an activity,
covering both queueing and processing. Case throughput time is therefore the sum
of its activity durations, and the two figures are consistent by construction.

Durations are drawn from per-activity triangular distributions rather than one
shared uniform range. This matters methodologically: with a single range, every
activity converges on the same mean and the bottleneck ranking becomes an
artefact of sampling noise. An earlier draft had exactly this defect — all P1
activities showed means between 22 and 32 hours, and the "bottleneck" was
whichever activity happened to draw high. Bottlenecks must originate in the
process model, not in the sampling.

### F.3.4 Modelling concurrency in P2

P2's two verification activities sit on parallel branches after D's Parallel
Gateway. Emitting them in a fixed order would make the log describe a sequence,
and no discovery algorithm could then recover the concurrency.

They are therefore modelled as genuinely concurrent: both start when document
checking completes, each is stamped at its own completion time, and they are
written in completion order, which varies per case. `Combine Verification
Results` cannot start until the later branch finishes, so the synchronisation
wait is an emergent property of the model rather than an inserted constant.

### F.3.5 Designed variants

Designed variants are labelled in the `variant` column. A designed variant is
not the same object as a discovered control-flow variant, and §F.7 reports the
two separately.

**P1** — 100 cases:

| Variant | Cases | Distinguishing feature |
|---|---|---|
| V1 Direct approval | 45 | No supplement, approved |
| V2 Single supplement | 20 | One document request cycle |
| V3 Review rejection | 15 | Rejected after review |
| V4 Multiple supplements | 10 | Two cycles |
| V5 Identity failure | 6 | Rejected at identity validation; no document check |
| V6 Delayed review | 4 | Same path as V1, review inflated 2.5x |

**P2** — 100 cases:

| Variant | Cases | Distinguishing feature |
|---|---|---|
| V1 Direct approval | 38 | Both verifications pass |
| V2 Document supplement | 22 | One document request cycle |
| V3 Employment ineligible | 16 | Rejected after review |
| V4 Housing ineligible | 12 | Rejected at assessment, before review |
| V5 Parallel branch delay | 8 | Employment branch inflated 2.5x |
| V6 Document rejection | 4 | Rejected at document check; no verification |

### F.3.6 Validation gate

`normalize_logs.py` applies eight checks. A log failing any error-level check is
not exported, so a defective log cannot silently reach the analysis.

| Code | Check | Why it matters |
|---|---|---|
| C1 | Required fields present | Mining cannot proceed without them |
| C2 | Activity names match BPMN Task names exactly | The traceability link between the BPMN chapter and this one |
| C3 | Resource matches the BPMN lane owning the task | Detects lane assignment drift |
| C4 | Timestamps parse, increase within a case, consistent awareness | Out-of-order events corrupt every trace |
| C5 | Cases terminate in a recognised end activity | Detects truncated logs |
| C6 | No duplicate (case, activity, timestamp) | Duplicates inflate frequencies |
| C7 | `application_status` in the §4.5 vocabulary | Keeps log and API state machines identical |
| C8 | ISO 8601 UTC with `Z` suffix | §4.2 |

C2 is the check that earns the gate its place. If B renames a P1 task without
telling the group, C2 fails immediately and blocks the analysis, instead of the
report presenting mining results whose activity names no longer match the BPMN
diagrams beside them.

The checks were verified by fault injection rather than by observing them pass.
Injecting a renamed activity, a non-Baseline status value and a naive local-time
timestamp produced errors C2, C7 and C4 and warning C8 respectively. That
exercise also exposed a defect in the validator itself: mixing timezone-aware
and naive timestamps raised an unhandled `TypeError` during ordering. It now
reports the condition as a C4 error.

Validated logs are exported as CSV and as XES 1.0, so they open in ProM as well
as PM4Py.

## F.5 Process Mining Method

### F.5.1 Tool selection

PM4Py was selected over ProM for three reasons: it runs in the same Python 3.12
environment as the rest of the project (§1.1), it can be scripted so the whole
analysis is reproducible from the command line, and it writes results directly
to JSON for the Portal to consume. ProM interoperability is retained through XES
export, so results can be cross-checked in a GUI tool if required.

### F.5.2 Algorithm selection

The **Inductive Miner** is used for discovery, in preference to the Alpha Miner
covered in the course.

The decisive reason is loops. P1's document supplement path revisits `Check
Submitted Documents` after `Submit Additional Documents`, and 30% of P1 cases
contain such a cycle. The Alpha Miner cannot correctly discover loops of length
one or two, and would produce an unsound model on this log. The Inductive Miner
handles arbitrary loops and guarantees a sound, block-structured workflow net,
so the discovered model is always executable — a property required for the
replay-based conformance measurement in §F.9.

The Inductive Miner also recovers concurrency, which is necessary for P2: it must
represent the two verification activities as parallel rather than inferring a
spurious ordering from whichever sequence happens to be more frequent.

### F.5.3 Pipeline

```
B's P1 log ─┐
            ├─> normalize_logs.py ─> validated CSV + XES ─> analysis.py ─> analytics.json
D's P2 log ─┘         (C1-C8)                                   │
                                                                └─> Petri nets (PNG)
```

Six analyses run over each validated log: control-flow variant analysis,
performance and bottleneck analysis, parallel synchronisation analysis (P2),
outcome analysis, resource analysis, and conformance checking by two
independent methods.

## F.6 Process Discovery

Both models were discovered by the Inductive Miner and rendered to
`process-mining/output/`.

| | P1 | P2 |
|---|---|---|
| Places | 9 | 14 |
| Transitions | 11 | 16 |
| Silent transitions | 2 | 4 |
| Visible transitions | 9 | 12 |
| Distinct activities in log | 9 | 12 |

Visible transitions equal the distinct activity count in both models: every
observed activity appears exactly once, with no duplication.

**P1** requires only 2 silent transitions, reflecting a largely sequential
process with two exclusive choices (identity outcome, approval outcome) and one
loop. The loop construct in the discovered model corresponds to B's document
supplement path, and its presence confirms that the cyclic behaviour in the log
was recovered structurally rather than flattened into repeated sequence.

**P2** requires 14 places and 4 silent transitions for 12 activities. The
additional structure is the concurrency construct: silent transitions implement
the split and join around the two verification branches. This is the discovered
counterpart of D's Parallel Gateway, recovered from nothing but the varying order
of branch completions in the log.

## F.7 Variant Analysis

### F.7.1 Designed versus discovered variants

The two views differ in both directions, and the difference is informative
rather than an error:

| | Designed | Discovered control-flow |
|---|---|---|
| P1 | 6 | **5** |
| P2 | 6 | **9** |

**P1 collapses.** V6 Delayed Review differs from V1 only in the duration of
`Review Application`; its activity sequence is identical, so the two share one
control-flow trace. Control-flow discovery is blind to time, and a purely
temporal variant is invisible to it. V6 is recovered instead by the performance
analysis in §F.8.

**P2 expands.** Its parallel verification branches complete in whichever order
the durations dictate, so a single designed variant appears as two traces. Six
designed variants become nine observed traces. Concurrency multiplies observable
traces without adding modelled behaviour — which is precisely why the Inductive
Miner's concurrency construct matters: it collapses those nine traces back into
one model rather than presenting nine special cases.

An earlier draft of this report claimed six variants for both processes,
inherited from the design intent rather than measured from the log. Both figures
were wrong, and in opposite directions.

### F.8.1 Throughput time

| Metric | P1 | P2 |

| Mean | 6.3 days | 5.7 days |
| Median | 5.4 days | 5.3 days |

cases — rather than to attempt to speed the step up.

`Check Submitted Documents` shows 134 occurrences across 100 cases, direct
evidence of the supplement loop re-entering the check.

### F.8.4 Cost of the parallel gateway

Per-activity statistics cannot express the cost of D's Parallel Gateway, because
the cost falls on neither branch. The join cannot fire until the slower branch
completes, so the faster branch's output waits.

| Metric | Value |
|---|---|
| Cases with both branches | 96 |
| Mean idle wait at join | 20.0 h |
| Median idle wait | 14.2 h |
| Maximum idle wait | 93.0 h |
| Employment slower | 52 cases |
| Housing slower | 44 cases |

A mean of 20 hours is lost per case to branch desynchronisation, reaching 93
hours at worst. Neither department is systematically slower — the split is 52 to
44 — so this is inherent variance between two independent agencies, not one
department underperforming.

The design implication is that parallelising the two verifications does help:
sequential execution would cost the sum of both durations rather than the maximum
plus a wait. But the benefit is bounded by the slower branch, so the gateway
converts a summation into a maximum rather than eliminating the delay.

## F.9 Conformance Checking

### F.9.1 Two methods, and why one alone is insufficient

Conformance is measured twice, because the obvious measurement answers a weaker
question than it appears to.

**Token-based replay** against the Inductive Miner model:

| | P1 | P2 |
|---|---|---|
| Mean trace fitness | 1.0 | 1.0 |
| Perfectly fitting cases | 100.0% | 100.0% |

These values are near-certain in advance. The model was discovered *from this
same log*, and the Inductive Miner guarantees a sound net that reproduces its
input. A fitness of 1.0 therefore confirms that discovery succeeded and the log
is internally consistent; it does **not** establish that the process matches what
B and D designed. Reporting it alone — as an earlier draft did, with an invented
figure of 0.94 — would overstate what had been verified.

**Designed-path comparison** is the check that answers the real question. The
control-flow paths permitted by the P1 and P2 BPMN models are enumerated
independently in `analysis.py`, and every observed trace is tested for membership:

| | P1 | P2 |
|---|---|---|
| Designed paths enumerated | 7 | 13 |
| Conformant cases | 100 (100.0%) | 100 (100.0%) |
| Deviating cases | 0 | 0 |

P2 requires 13 enumerated paths against P1's 7 largely because both interleavings
of the parallel branch must be admitted as conformant — the same trace
multiplication seen in §F.7, appearing here as a requirement on the conformance
model rather than as an observation.

### F.9.2 Interpretation and limits

100% conformance is the expected and correct result for a generated reference
log, since generator and conformance model derive from the same BPMN
specification. It demonstrates that the pipeline is sound and that the
enumeration matches the generator, and it establishes the baseline against which
B's and D's real logs will be compared.

It is not evidence about real-world execution. Its diagnostic value is negative:
when the real logs are validated, any figure below 100% localises a genuine
disagreement between implemented behaviour and designed behaviour, and the
deviating traces are reported explicitly so the responsible member can act. The
value of this check lies in what it will detect, not in the reference figure it
currently reports.

| Approval rate | 79.0% | 68.0% |
| Rejection rate | 21.0% | 32.0% |
| Supplement rate | 30.0% | 22.0% |
| Rework rate | 30.0% | 22.0% |
| Dominant time consumer | Review Application (63.5%) | Verification pair (58.3%) |
| Structural conformance | 100.0% | 100.0% |

P2's lower approval rate (68% against 79%) follows from its structure: it has two
independent eligibility gates, each capable of rejecting an application, whereas
P1 has one substantive review. More gates produce more rejections.

The two processes concentrate delay differently. P1 has a single dominant
activity at 63.5% of elapsed time, so improvement there is a matter of one
queue. P2 distributes delay across two agencies plus a synchronisation wait, so
no single intervention addresses it.

## F.11 Demonstration Description

### F.11.1 Structure

The demonstration is a single continuous scenario following one fictional new
resident through the full service journey: profile creation, residence
registration, employment status query, housing subsidy application, aggregated
status via the Gateway, service recommendation, and process analytics.

Ten scenes are allocated across eight segments so that every member presents
their own contribution, within a 9:30 budget against the 10:00 limit. F records
the Portal and analytics segments and assembles the whole. The storyboard,
including per-member timing, is in `demo/demo_storyboard.md`.

### F.11.2 Backup data

Application IDs are consumed on submission, so a restarted take can collide with
records created by the previous attempt. Two interchangeable datasets are
prepared, plus a third for demonstrating validation and error handling, in
`demo/backup_demo_data.md`.

### F.11.3 Quality gate

F owns the third of the project's three final quality gates. It covers five
areas — route stability, visible coverage of every microservice, recording
quality, duration, and consistency between the demonstration and the report — and
is recorded in `docs/uat/demonstration_quality_gate.md` for sign-off before
recording rather than on submission day.

The consistency checks matter most, because a mismatch between what the video
shows and what the report claims is the one inconsistency an examiner encounters
without reading any code. Two are enforced mechanically rather than by
inspection: activity names shown on screen must match BPMN task names, which
check C2 guarantees, and analytics figures shown must match the report, which
holds because both read `analytics.json`.

### F.12.1 Limitations

Three items remain outstanding, all with external dependencies:

1. **Portal screenshots** require E's integrated release, since screenshots of a
   Portal returning only error envelopes would be worthless.
2. **The four backend-dependent UAT cases** are BLOCKED for the same reason.
3. **The final video** is scheduled after system function freeze, per the project
   timeline.

A methodological limitation should also be stated plainly: the analysis in
§F.6–F.9 is performed on generated reference logs, not on execution traces from
the running services. The figures characterise the modelled processes and
validate the analysis pipeline; they are not empirical measurements of the
implemented system. When B and D deliver real logs, the same pipeline runs
unchanged via `normalize_logs.py --incoming`, and the conformance figures then
become substantive rather than confirmatory.
