# CityStart Portal + Process Analytics (Part F)

**Role:** Portal and Process Analytics Lead / Demonstration and Video Lead

## Technical Baseline compliance

This module follows the CityStart Technical Baseline. The points that constrain F:

| Clause | Requirement | How this module complies |
|---|---|---|
| §1.4 | HTML + Bootstrap + JavaScript `fetch`, no React/Vue | Jinja2 templates, Bootstrap 5.3 from CDN, plain `fetch` in `static/js/main.js` |
| §2 | Portal on port **3000**; addresses via env vars | `PORT=3000` default; Gateway from `API_GATEWAY_URL`; nothing hard-coded in page logic |
| §3.3 | Portal must not touch business databases | No DB driver in `requirements.txt`; Portal holds no persistent state |
| §4.1 | `snake_case` field names | All request bodies use `snake_case` |
| §4.2 | ISO 8601 timestamps | Event logs emit `...Z` UTC; `formatTimestamp()` renders them locally |
| §4.5 | Lowercase status vocabulary | `STATUS_LABELS` in `main.js` maps exactly `pending`, `under_review`, `approved`, `rejected`, `additional_documents_required` |
| §4.6 | Unified error envelope | `_error()` in `app.py` emits `{"error":{"code","message","details"}}`; `extractError()` parses it |
| §5 | Portal may only call the Gateway | `/api/proxy/*` is the only outbound route. The former `/api/direct/*` debug bypass was **removed** |
| §6 | Minimum deliverables | Source, `requirements.txt`, README, `.env.example`, sample data, test evidence — all present |

## Quick start

```bash
# 1. Event logs and analysis
cd process-mining
pip install -r requirements.txt
python generate_logs.py      # reference logs (seed 20260803)
python normalize_logs.py     # validation gate -> logs/validated/ + XES
python analysis.py           # -> output/analytics.json (+ copy to Portal)

# 2. Portal
cd ../citystart-portal
pip install -r requirements.txt
copy .env.example .env       # cp on Linux/macOS
python app.py                # http://localhost:3000
```

Petri net rendering needs Graphviz on `PATH` (`winget install Graphviz.Graphviz`).
Everything else works without it; `analysis.py` degrades gracefully and records
the reason in `analytics.json`.

### Integrating B's and D's real logs

```bash
# copy B's P1 log and D's P2 log into logs/incoming/, then:
python normalize_logs.py --incoming
python analysis.py
```

`normalize_logs.py` refuses to export a log that fails any check, so a
mismatched activity name is caught before it can reach the report.

## Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `3000` | Portal listen port (Baseline §2) |
| `API_GATEWAY_URL` | `http://localhost:8000` | Gateway base URL |
| `GATEWAY_TIMEOUT_SECONDS` | `30` | Upstream timeout before `GATEWAY_TIMEOUT` |
| `FLASK_DEBUG` | `0` | Set `1` for auto-reload in development |
| `PORTAL_TRUST_ENV_PROXY` | `0` | Set `1` only if the Gateway is genuinely behind an HTTP proxy |

> `PORTAL_TRUST_ENV_PROXY` defaults to off deliberately. With a system proxy
> active (VPN / clash-style tools), a stopped Gateway otherwise returns the
> proxy's own non-JSON 502 and is misreported as `GATEWAY_INVALID_RESPONSE`
> instead of `GATEWAY_UNAVAILABLE`.

## Error handling

`app.py` passes upstream errors through unchanged so the Gateway's envelope
reaches the browser intact. Only Portal-originated failures are generated
locally, all using the §4.6 shape:

| Code | HTTP | Cause |
|---|---|---|
| `GATEWAY_UNAVAILABLE` | 503 | Gateway not reachable |
| `GATEWAY_TIMEOUT` | 504 | No reply within `GATEWAY_TIMEOUT_SECONDS` |
| `GATEWAY_INVALID_RESPONSE` | 502 | Reply was not valid JSON |

## Reproducibility

`generate_logs.py` is seeded (`RANDOM_SEED = 20260803`), so every figure quoted
in the report can be re-derived. Do not change the seed after report figures are
finalised. The Process Analytics page and the report both read from
`analytics.json`; no figure is typed by hand in either place.
